01

How a case actually moves through the system

One inbound event triggers a queued job, a LangGraph run through the interpreter, a write to Postgres, and — on a separate schedule, not inline — a merge into the Neo4j graph. Two of the arrows below are drawn as alternatives on purpose: today's graph sync re-polls Salesforce a second time for text the worker already captured.

03

Everything else: tenant_id + RLS, not foreign keys

Why there's no ER diagram past this point Outside the spine above, this schema deliberately doesn't foreign-key tables to each other — a review task's kb_change_id, a KB entry's supersedes_entry_id, an action request's run_id are all plain uuid columns with no constraint. Every table carries its own tenant_id and Postgres RLS (tenant_members) instead. That means a service-role write to one subsystem — KIL writing a review task, a connector sync updating tenant_integrations — never blocks on another table's row existing, at the cost of the database itself not being able to tell you these rows are related. The cards below are grouped by the domain that actually links them in code, not by a constraint Postgres enforces.
04

The Neo4j graph model

Two independent sync paths write into the same graph: case_graph_sync.py mirrors every case's full lifecycle and message thread (any status), and case_memory_sync.py embeds each resolved case and derives similarity edges. Counts below are live, read from the connected graph.

05

Who owns what

The rule the rest of this map is built to enforce: no two systems hold a conflicting copy of the same fact. Everyone else holds a reference, not a second original.

FactSystem of recordEveryone else holds
The case, the email, CaseComments, Chatter Salesforce / Zendesk A reference — Case / EmailMessage id
Flow execution state, what the pipeline decided and why, the human's resolution text Supabase runs This is the flow history — nothing upstream re-derives it
Relationships + semantic similarity between cases Neo4j Bounded, redacted excerpts + a pointer back to run_id / Case id
The human collaboration thread Slack Nothing syncs in — Slack's own history is its own audit trail
Knowledge base content Supabase kb_entries Neo4j can link a Case to the KB entry it resolved via — never holds KB text
A tenant's own product usage (planned) Tenant's Mixpanel / GA4 Neo4j Event nodes correlated to Contact/Account — not a warehouse copy
